The task is to fix the browser abort caused by a WebAssembly atomic operation reaching an unaligned guest address. I treated the two BusDK research notes as authoritative. The relevant rule is that ordinary WebAssembly loads and stores tolerate misalignment, but WebAssembly atomics require natural alignment and trap otherwise. RV64 A-extension atomics also require natural alignment unless an optional misaligned atomicity granule is deliberately modeled, which this accelerator path does not do.

## Work Narrative

I first verified the local QEMU instructions in `AGENTS.md`, then read the two research notes from the BusDK checkout because the `../busdk/docs/docs/research` relative path named in the QEMU guidance is not materialized inside this runtime. The plan records the same failure mode: a generated-exec preflight reached `generated_run_entries=1` and then aborted with `RuntimeError: operation does not support unaligned accesses` before a useful boot milestone.

The code search showed that the hand-written generated-body module emitter emits plain loads and stores plus an `atomic.fence`, but no direct guest atomic RMW byte sequence. The unsafe path is therefore the common TCG guest atomic helper path: when `CF_PARALLEL` is set, `tcg_gen_atomic_*` emits helper calls that eventually use QEMU `qatomic_*`; in an Emscripten build those become WebAssembly atomics. The existing QEMU serial fallback path is already available through `gen_helper_exit_atomic(tcg_env)`, and serial re-execution clears `CF_PARALLEL`, reducing atomicity before lowering.

I patched `tcg/tcg-op-ldst.c` with a wasm64-only predicate that requires natural guest alignment metadata before the helper-backed atomic path may remain. If `memop_alignment_bits(memop)` is weaker than the access size, every common atomic emission helper now emits `exit_atomic` and produces a dead-code result for liveness. This covers cmpxchg, xchg, and fetch/fetch-returning atomic families for 32-, 64-, and 128-bit forms. This keeps naturally aligned frontends, such as RV64 AMO paths carrying `MO_ALIGN`, eligible for the helper path while forcing default `MO_ATOM_IFALIGN` paths such as x86 locked operations into serial fallback unless a future patch adds an explicit alignment proof.

I also extended `scripts/ci/wasm64-translate-metadata-test.mjs` with source-contract assertions so the wasm64 guard and its coverage of the common atomic helper families cannot disappear silently.

## Direction Correction

After the first implementation pass, the user supplied stronger evidence that corrected the initial task brief. The failing stack frames are static indices in the main Emscripten-compiled `qemu-system-riscv64.wasm`, so the unaligned WebAssembly atomic is C-level static code, not a generated wasm guest-atomic byte sequence. That also matches the existing generated-body validator: atomic MemOps are rejected before generated byte emission, and generated bodies are supposed to emit only ordinary loads and stores.

Before that correction I had built an x86_64 artifact from the detour patch. The warm ccache build passed in 644.52 seconds, and a bounded Chrome run against that artifact timed out before the boot marker after 300 seconds. The result still showed useful movement, with `generated_run_entries=20600` and `generated_guest_instructions=34493`, and no immediate unaligned-access trap in that run. Because the detour patch could mask the true static C site through the fallback path, I removed the changes from `tcg/tcg-op-ldst.c` and the temporary metadata-test assertions before continuing.

The next phase is instrumentation rather than speculation: build a symbolized artifact with Emscripten function names (`-g2` and `--profiling-funcs` on the existing warm build path), rerun the live-generated-exec browser preflight, and resolve `wasm-function[1403]` to the C symbol that actually traps. In parallel, a read-only thread is scanning `tcg/wasm64.c` and adjacent live-exec helpers for `qatomic_*`, `_Atomic`, `__atomic`, or wide reads over potentially unaligned metadata and TB-code pointers. The intended fix is the smallest alignment-safe change at the named static C site: byte-wise or `memcpy` access where the data may be unaligned, or a narrow fail-closed guard if the path cannot safely proceed.
